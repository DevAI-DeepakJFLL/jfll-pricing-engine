# Air Export Pricing Engine — Codebase Audit & Root-Cause Analysis

**Scope:** `README.md`, `AIR_EXPORT_PRICING_ML_DOCUMENTATION.md`, `preprocess.py`, `train.py`, `engine.py`, `app.py`, `Air_Export_Pricing_Cleaned_ML.csv`, `freight_margin_recommender.joblib`
**Method:** Static review only — no code executed, no fixes applied.
**Legend — Priority:** 🔴 Critical (incorrect recommendations / broken UX) · 🟠 High (silent data quality or drift risk) · 🟡 Medium (design smell / maintainability) · ⚪ Low (cosmetic / dead code)

---

## 1. Model Training (`train.py`)

| # | Finding | Priority | Reason Flagged | Business / Technical Impact |
|---|---|---|---|---|
| 1.1 | **`OrdinalEncoder` is fit only on `df_won` (won deals), not the full dataset** (lines 60–64) | 🔴 Critical | `cat_cols` categories are learned exclusively from the won-deals subset. Any category value that appears only in *lost* deals (a losing lane, a customer tier only ever seen in a loss) is unseen at fit time. | Both Stage 1A (benchmark regressor) and, indirectly, Stage 1B (classifier — reuses the same encoder) will map these categories to `-1` (unknown). This silently discards exactly the "loss" signal that the project's own documentation (Section 6, Survivorship Bias) identifies as essential. The model is *structurally* biased toward won-deal geography/customer patterns despite being trained on a supposedly balanced dataset. |
| 1.2 | **`Margin_Ratio` (the classifier's key monotonic feature) is computed from a benchmark that itself has survivorship bias** (lines 66–69, depends on 1.1) | 🔴 Critical | The classifier's win-probability curve is anchored to "how far above/below the won-deal benchmark" a margin sits. If the benchmark itself is skewed high (never having learned where deals were lost), every downstream `Margin_Ratio` is systematically distorted. | This compounds 1.1 one layer deeper into the architecture that the documentation explicitly warns against. The core optimization primitive (`Expected Profit = Margin × P(Win)`) inherits this bias, so *quoted margins can be recommended too high on lanes/segments where the true willingness-to-pay is lower than the won-only benchmark suggests.* |
| 1.3 | **Inconsistent margin clipping bounds between training and inference** — `train.py` clips `y_won` to `[0.5, 50.0]` (line 62); `engine.py` clips `benchmark_margin` to `[1.5, 45.0]` (line 40) | 🟠 High | Two different valid ranges for conceptually the same quantity, defined in two different files with no shared constant. | Any regressor output between 45–50% or below 1.5% is silently re-clamped at inference time in a way that doesn't match what the model was trained to produce — the model can "believe" a 48% benchmark is valid, but `engine.py` will never surface it. Not model-breaking, but a subtle contract mismatch that will resurface as confusing behavior if either bound is edited independently later. |
| 1.4 | **`sklearn` version skew between training and current runtime** (confirmed via artifact inspection: joblib pickled with `scikit-learn==1.9.1`, environment has `1.8.0`) | 🟠 High | `InconsistentVersionWarning` fires on load for `_BinMapper`, `HistGradientBoostingRegressor`, `HistGradientBoostingClassifier`, `LabelEncoder`, `_SigmoidCalibration`, `CalibratedClassifierCV`, and `OrdinalEncoder`. | Pickled sklearn estimators are not guaranteed binary-compatible across minor versions. This can cause silent numerical drift, subtly wrong `predict_proba` outputs, or outright load failures in different environments — a live production risk independent of the modeling logic itself. |
| 1.5 | **Magic-number monotonic constraint with no backtest validation** — `monotonic_cst` forces strictly decreasing win-probability on `Margin_Ratio` (lines 96–98) | 🟡 Medium | Directionally sound (higher relative margin *should* reduce win rate), but the constraint is applied without any check that it doesn't clash with real patterns in the data (e.g., "premium" segments in Section 7 of the documentation, like customs clearance at 31–50% margin, may violate simple monotonicity relative to a single ratio). | Could be silently degrading calibration quality on exactly the segments (perishables, key accounts) the documentation calls out as legitimately non-linear. Not necessarily wrong, but undocumented and unvalidated. |
| 1.6 | **No holdout evaluation of Stage 1A (benchmark regressor)** — only Stage 1B (classifier) gets a train/test split and AUC/Brier metrics (lines 74–86) | 🟡 Medium | The regressor that anchors the entire margin search space (`engine.py`'s `min_m`/`max_m` window is centered on `benchmark_margin`) has zero quantitative validation in the training script. | There's no way to know from this pipeline alone whether the benchmark regressor is accurate, overfit, or systematically biased by region/customer tier — yet the whole candidate search space depends on it. |

## 2. Data Preprocessing (`preprocess.py`)

| # | Finding | Priority | Reason Flagged | Business / Technical Impact |
|---|---|---|---|---|
| 2.1 | **Categorical string values used for feature engineering here don't match the categorical values the UI later submits** (root cause confirmed by cross-referencing `preprocess.py`'s region-mapping keyword lists against `app.py`'s dropdown option values and the trained encoder's `categories_`) | 🔴 Critical | `preprocess.py` derives `Origin_Port`/`Destination_Port` from raw historical data, producing values like `"Bangalore"`, `"Dubai"`, `"Delhi"` in most cases — but `app.py`'s dropdown supplies full airport names like `"Kempegowda International Airport"`, `"Heathrow Apt/London"`, `"John F Kennedy International Airport"`, most of which are **not** in the fitted encoder's vocabulary. | This is very likely the single biggest driver of "incorrect recommendations": every UI submission using a full airport name for a port not already stored that way collapses to `unknown_value=-1` in the encoder, meaning the model receives no real route signal for that inquiry. Confirmed directly against the joblib artifact (see §3 below). |
| 2.2 | **No single source of truth for the weight-tier bins** — the bin boundaries `[0, 45, 100, 300, 500, 1000, ∞]` are hardcoded independently in `preprocess.py` (`pd.cut`, lines ~with `bins`/`labels`) and re-implemented as manual `if/elif` in `app.py` (lines 901–912) | 🟠 High | Duplicated business logic with no shared constant or function. | Currently consistent, but this is a landmine: any future edit to weight-tier thresholds in one file without the matching edit in the other will silently desync training-time feature meaning from inference-time feature meaning, producing wrong tier labels with no error raised anywhere. |
| 2.3 | **Regional mapping functions rely on brittle substring/keyword matching** (`map_origin_region`, `map_dest_region`, lines ~with `any(k in o for k in [...])`) | 🟡 Medium | These are duplicated verbatim between `preprocess.py` and `app.py` (good for consistency) but are fragile: e.g., `"amman"` matches Middle East, but a city name substring collision (a made-up example: any destination string containing `"oman"` as a substring of a longer word) could silently misclassify. No unit tests or exhaustive validation against the full port list. | Misclassification here silently corrupts `Origin_Region`/`Destination_Region`/`Regional_Lane`, which feed directly into both model stages. Low current risk given curated keyword lists, but no guardrail exists to catch a bad match. |
| 2.4 | **`Weight_Tier` is a pandas `Categorical` dtype after `pd.cut`, then coerced via `.astype(str)` only downstream in `train.py`** | 🟡 Medium | Type handling (Categorical → object/string) happens implicitly across file boundaries rather than being made explicit in `preprocess.py`'s own output contract. | Works today, but is an easy place for a silent `NaN`/`"nan"`-string bug to creep in if `pd.cut`'s `right=False` boundary behavior or bin edges are ever changed without re-checking both files. |
| 2.5 | **Post-hoc leakage columns correctly excluded, but no automated leakage check** (`Loss Reason`, `Loss Remarks`, `TAT to Close` — documented as excluded in the markdown, and absent from `output_cols`, lines with `output_cols = [...]`) | ⚪ Low | Handled correctly in the current column list, but the exclusion is enforced only by the static `output_cols` list, not by any automated leakage-detection logic. | Low current risk since it's done correctly today, but there is no test that would catch a future contributor accidentally re-adding a leakage column to `output_cols`. |

## 3. Confirmed Cross-Artifact Mismatch (Preprocessing ↔ UI ↔ Model)

*(Direct evidence from inspecting the shipped `freight_margin_recommender.joblib`.)*

| # | Finding | Priority | Reason Flagged | Business / Technical Impact |
|---|---|---|---|---|
| 3.1 | **Trained `Origin_Port` vocabulary is a mix of city names and full airport names, inconsistent with `app.py`'s dropdown values** — confirmed categories include `'Bangalore'`, `'Dubai'`, `'Delhi'`, `'Chennai'`, `'Mumbai'`, `'Kolkata'`, `'Hyderabad'`, `'Cochin'` alongside a few full names like `'Chhatrapati Shivaji Maharaj International Airport'` and `'Kozhikode (ex Calicut)'` | 🔴 Critical | Direct output of `enc.categories_` vs. direct read of `app.py`'s `<option value="...">` attributes. Most UI dropdown values (`"Kempegowda International Airport"`, `"Zayed International Airport"`, `"Heathrow Apt/London"`, `"John F Kennedy International Airport"`, `"Pearson International Apt/Toronto"`) have **no exact match** in the trained vocabulary. | Every quote generated through the web UI for these routes is silently scored using an "unknown route" signal rather than the real one — the model cannot use its learned route-level pricing knowledge for the majority of the UI's own preset destinations, undermining the tool's core value proposition. |
| 3.2 | **`Booked by branch` trained vocabulary is limited to 11 branches** (`Ahmedabad, Bangalore, Calicut, Chennai, Cochin, Delhi, Hyderabad, Kannur, Kolkata, Mumbai, Trivandrum`), while `app.py`'s branch dropdown only offers 5 (`Mumbai, Delhi, Bangalore, Ahmedabad, Chennai`) | 🟡 Medium | Confirmed via artifact inspection vs. dropdown HTML. Not a mismatch causing `-1` encoding (all 5 UI options are valid trained categories), but it means the UI arbitrarily restricts access to branches the model actually has learned behavior for. | Understates the tool's usable scope rather than corrupting predictions — a usability gap, not a correctness bug, but worth flagging since it's the same class of root issue as 3.1 (UI option lists drifting from the training vocabulary). |

## 4. Recommendation Engine (`engine.py`)

| # | Finding | Priority | Reason Flagged | Business / Technical Impact |
|---|---|---|---|---|
| 4.1 | **Unvalidated, hardcoded "retention weight" heuristic** — for `Customer_Inquiry_Frequency > 15`, margins above `1.8×` benchmark get their expected profit multiplied by `0.85` (lines ~79–84) | 🟠 High | This is a business rule dressed as a data-driven adjustment. There is no evidence in `train.py` or the documentation that `0.85`, `15`, or `1.8×` were derived from actual retention/churn data — they appear to be arbitrary constants. | Directly changes which margin gets recommended for ~any "Key Account" tier customer (frequency ≥ 20 per the documented tiering) bidding above a threshold, without a data-backed justification. Could either help (protecting LTV, as intended) or hurt (leaving profit on the table) — impossible to know without a backtest, which doesn't exist. |
| 4.2 | **Multiple undocumented magic-number guardrails in `optimize_quote`** — `max_win_prob < 0.015` collapse-detection threshold, `dynamic_floor = max(0.05, max_win_prob * 0.60)`, and `effective_floor = min(min_win_prob, max_win_prob * 0.85)` (lines ~90–110) | 🟠 High | None of these constants (`0.015`, `0.60`, `0.05`, `0.85`) are derived, documented, or configurable — they materially shape which margin is ultimately recommended in edge cases (thin/collapsed win-probability curves). | These thresholds directly decide the fallback behavior when the model is least confident — exactly the situations where a wrong constant does the most damage (recommending an unrealistic margin when the classifier has effectively no signal). |
| 4.3 | **`STRATEGY_THRESHOLDS` (`volume`/`balanced`/`skimmer`) are fixed win-rate floors with no empirical grounding referenced** (lines ~15–19) | 🟡 Medium | Same class of issue as 4.1/4.2 — plausible business defaults, but presented without justification or a way to tune them from data. | Changes the recommended margin meaningfully depending on which strategy a user selects, but the underlying `0.40 / 0.25 / 0.15` values are opaque assumptions, not calibrated outputs. |
| 4.4 | **Inconsistent clipping range vs. `train.py`** (see 1.3 — cross-referenced here for completeness) | 🟠 High | Same finding as 1.3, listed here because the actual clamping happens in this file. | See 1.3. |

## 5. UI / UX (`app.py` — Flask templates & client-side JS)

| # | Finding | Priority | Reason Flagged | Business / Technical Impact |
|---|---|---|---|---|
| 5.1 | **Dropdown option values are decoupled from the trained model's categorical vocabulary** (root UI-side cause of §3) | 🔴 Critical | The `<option value="...">` strings were evidently chosen for human readability in the UI rather than sourced from the actual trained `encoder.categories_`. | This is the actionable, UI-side half of the biggest correctness issue in the whole system (§3.1) — fixing this (or fixing the encoder's vocabulary to match) is likely the single highest-leverage change available. |
| 5.2 | **No client-side or server-side validation `pattern`/`type` constraints on numeric-looking text inputs** (`buy`, `gross_wt`, `dim_l/w/h`, `frequency`, `revision` are all `type="text"`, not `type="number"`, with no `pattern`, `inputmode`, or `min`/`max` attributes) | 🟠 High | The header comment block in `app.py` (lines 5–9) explicitly claims this was a deliberate design choice "to bypass WebKit validation friction," but it removes the browser's built-in guardrails against malformed input, pushing all correctness burden onto regex-based JS/Python parsing (`parseNum`, `parse_clean_float`) with silent-default fallback behavior. | This combination (no native validation + regex-strip-and-default fallback + locale-aware `toLocaleString` formatting) is the most plausible source of the "string did not match the expected pattern" error reported by the user — it is a browser-native `Intl`/`RegExp`/constraint-validation message, not a Python traceback, and the surrounding code shows several places (locale formatting, manual regex parsing, empty-string reset flows) where malformed or edge-case input could trigger it. Root cause could not be fully isolated without executing code, per the audit's constraints. |
| 5.3 | **Silent-default fallback design masks bad input rather than surfacing it** — `parse_clean_float`/`parse_clean_int` and the JS `parseNum` all substitute a default value on any parse failure rather than raising a visible, user-facing validation error | 🟠 High | A user who types garbage into "Airline Buy Cost" gets a *silent* substitution to ₹100,000 with no on-screen indication that their input was discarded. | Directly produces "incorrect recommendations" from the user's perspective — the tool will confidently return a full sensitivity table computed against a default value the user never intended, with no error, warning, or highlighted field. |
| 5.4 | **`resetFormForNewQuote()` doesn't fully reset every field it later reads** — `dim_pcs` is reset to `'1'` (line 714) but `dim_l`/`dim_w`/`dim_h` are reset to `''`, and `updateDimensions()` is then called (line 728) before the select dropdowns are reset (lines 721–725 happen after) | 🟡 Medium | Minor ordering inconsistency; `parseNum` defaults absorb the empty strings so this doesn't currently crash, but the function's field-reset order doesn't match its own numbered comments (steps 1–6 aren't fully self-consistent with execution order). | Low functional impact today (defaults cover the gap), but a fragile pattern that could break silently if `updateDimensions()`'s default-handling is ever changed. |
| 5.5 | **`Margin_Percentage: 5.0` hardcoded, unused placeholder in the inquiry payload sent from `api_quote`** (line 925) | ⚪ Low | Dead value — `engine.optimize_quote` recomputes margin from the benchmark regressor and never reads this field from `inquiry_dict`. | No functional impact today, but a landmine for future maintainers who might reasonably assume this field does something. |
| 5.6 | **Triple-fallback path resolution for both `sys.path` and `MODEL_PATH`** (lines 28–30, 121–126) | 🟡 Medium | Suggests the actual deployed directory structure doesn't reliably match what `README.md` documents (a single, clean `air_export_pricing_engine/` layout). | Not a correctness bug, but a sign of an unstable/undocumented deployment story — makes it harder to reason about *which* model file is actually being loaded in a given environment. |
| 5.7 | **Manual regex-based `formatINR` fallback for `toLocaleString('en-IN')`** (JS lines 584–591) | 🟡 Medium | A `try/catch` with a hand-written comma-insertion regex fallback, seemingly added to work around a WebKit issue, but the actual failure mode it's guarding against isn't documented or reproduced anywhere in the codebase. | Adds complexity without a clearly diagnosed trigger condition — see 5.2, this is one of the more likely locations for the reported "pattern" error given it directly wraps a locale-sensitive `Intl` call. |

## 6. SQLite History Subsystem (`app.py`)

| # | Finding | Priority | Reason Flagged | Business / Technical Impact |
|---|---|---|---|---|
| 6.1 | **Entire history/CRM subsystem is out of scope of the stated ML objective** — schema definition, auto-migration logic, a second full HTML template (`HISTORY_TEMPLATE`), and four REST endpoints (`/history`, `/api/history/update_status`, `/api/history/clear`, `/api/history/export`) — roughly half of `app.py`'s 1,378 lines | 🟡 Medium | None of this is mentioned in `README.md` or the ML documentation, which describe the project purely as a margin-recommendation engine. | Not wrong, but a significant, undocumented scope expansion that roughly doubles the file's size and the surface area for bugs — including plausible contributors to the reported client-side error, since this subsystem does its own separate JSON parsing/formatting (`updateLeadStatus`, `clearHistory` in the JS, lines ~1192–1231). |
| 6.2 | **`log_recommendation` swallows all exceptions with a bare `except Exception` and only logs a warning** (lines 112–113) | 🟠 High | Any failure writing to the history DB — including a real data-integrity bug — is invisible to the end user and only surfaces as a log line. | Silent failure mode: the "audit trail" this subsystem exists to provide can quietly stop working (e.g., due to a schema mismatch after a manual DB edit) with zero visible signal, undermining its own purpose. |
| 6.3 | **Schema auto-migration logic (`ALTER TABLE ... ADD COLUMN status`) runs unconditionally on every app startup** (lines 74–78) | 🟡 Medium | Defensive migration code is reasonable, but it's unversioned — there's no migration history/tracking, so future schema changes will require hand-editing this same ad hoc pattern. | Works fine at current schema complexity (one column), but doesn't scale as a migration strategy and has no rollback path. |
| 6.4 | **No foreign-key or referential integrity between the recommendation history and the actual model version/artifact used to generate it** | 🟡 Medium | `recommendation_history` stores only the output numbers, not which model artifact (or `sklearn` version — see 1.4) produced them. | If the model is retrained and redeployed, historical records become impossible to audit against "what the model actually believed at the time" — a meaningful gap for a tool whose stated purpose includes negotiation/audit tracking. |
| 6.5 | **CSV export (`/api/history/export`) and the update-status endpoint both re-derive/duplicate status-string logic already present elsewhere** (`get_status_class`, `statusMap` in JS, the `valid_statuses` list in `api_history_update_status`) | ⚪ Low | Status vocabulary (`"Draft / Quoted"`, `"Won"`, `"Lost"`, etc.) is defined independently in at least three places (Python `valid_statuses` list, Python `get_status_class`, JS `statusMap`). | Low immediate risk, but the same "duplicated business logic across files" pattern seen in §2.2 — a future status-value change in one location without the other two will desync validation from display. |

**On the reported "string did not match the expected pattern" error:** the strongest evidence points to a **client-side JavaScript/`Intl` locale-formatting issue** (§5.2, §5.7), most likely triggered through `formatINR()`'s `toLocaleString('en-IN')` call or the unvalidated `type="text"` numeric inputs feeding it edge-case values — not a Python/Flask exception. This could not be fully isolated without executing code, per this audit's constraints, and should be the first item confirmed via runtime reproduction before a fix is proposed.
